# Phase 02.2: Home and Search Motion Audit - Research

**Researched:** 2026-03-11
**Domain:** Next.js App Router marketing shell motion, framer-motion accessibility/performance, travel discovery UI cohesion
**Confidence:** MEDIUM-HIGH

## Summary

Phase `02.2` should be planned as a **discovery-shell polish phase**, not as a feature-expansion phase. The highest-leverage move is to establish a small motion/design contract first, then implement the homepage hero and the shared header/search shell against that contract. This keeps the brand system coherent and prevents ad hoc animation from leaking into conversion-critical interactions.

The existing codebase already has the right primitives for this work:
- `framer-motion` is installed and already used in `hero-search-bar.tsx`
- the homepage is server-rendered and segmented into reusable content modules
- the header already has clear route-aware logic, including compact search on non-home pages and checkout suppression

The provided `Hero`, `ScrollExpandMedia`, and `Globe` samples should be treated as **pattern references** only. Their strongest reusable ideas are rotating value-language, cinematic media framing, and atmospheric travel/world cues. The `ScrollExpandMedia` sample specifically uses wheel/touch interception and scroll trapping, which is a poor fit for this product and should not be carried forward.

**Primary recommendation:** plan this phase around an audit/design contract in Wave 1, then split implementation into homepage motion and header/search-shell polish in Wave 2. Keep motion transform/opacity-based, respect reduced motion, and avoid any interaction that competes with destination entry or search completion.

## Architecture Patterns

### Pattern 1: Audit-First Motion Contract
**What:** Lock palette, typography, motion timing, reduced-motion behavior, and shell constraints before implementation.
**When to use:** At the start of the phase before editing homepage or header code.
**Why:** Prevents visually disconnected work across homepage and compact search shell.

### Pattern 2: Server-Composed Hero, Client-Scoped Motion
**What:** Keep the homepage shell server-rendered and isolate only the motion logic that actually requires client execution.
**When to use:** Hero copy rotation, staged reveals, and any interactive hero media layer.
**Why:** Preserves fast initial render and avoids over-clientizing the homepage.

### Pattern 3: Conversion-Safe Motion
**What:** Use opacity/translate/scale on non-blocking surfaces only; never animate target position during input or trap scroll.
**When to use:** Search shell entrance, CTA emphasis, section reveal.
**Why:** Search is the core interaction; the motion should support intent, not compete with it.

### Pattern 4: Shared Shell Consistency
**What:** Homepage hero, compact header search, and supporting content modules should share a coherent surface language.
**When to use:** Header/search-shell polish after homepage motion work is defined.
**Why:** The current shell is functional but stylistically under-connected.

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| Scroll-locked cinematic hero | Custom wheel/touch interception layer | Passive media framing and standard page scroll | Scroll trapping is hostile to booking/search UX |
| Full-page client animation shell | One giant `use client` homepage | Server-first page with targeted client islands | Preserves performance and avoids unnecessary hydration |
| Novel iconography or emoji metaphors | Custom decorative icon set | Existing Lucide system and premium surface tokens | Keeps the brand coherent |
| Motion-heavy input choreography | Animated layout shifts around form controls | Stable layout with subtle opacity/transform emphasis | Prevents search usability regressions |

## Common Pitfalls

### Pitfall 1: Motion Overwhelms Search
**What goes wrong:** The hero feels impressive, but the user loses focus on destination/date/guest entry.
**How to avoid:** Search remains the visual and functional primary action above the fold.

### Pitfall 2: Scroll-Jacking from Media Experiments
**What goes wrong:** The page traps wheel/touch input or blocks standard browsing.
**How to avoid:** Explicitly ban wheel interception and scroll lock in the plan.

### Pitfall 3: Design-Language Drift
**What goes wrong:** The homepage becomes cinematic while the header/search shell still looks like a separate system.
**How to avoid:** Audit and implement homepage and shell against one motion contract.

### Pitfall 4: Reduced-Motion Neglect
**What goes wrong:** Rotating copy and section reveals become inaccessible or distracting for motion-sensitive users.
**How to avoid:** Provide static fallbacks and disable non-essential animation when reduced motion is requested.

### Pitfall 5: Mobile Overflow and Heavy Media
**What goes wrong:** Hero composition looks strong on desktop but spills, clips, or stutters on phones.
**How to avoid:** Validate 375px and 768px layouts explicitly and keep media treatment lightweight.

## Code Examples

### Safe rotating copy
```tsx
const reduceMotion = useReducedMotion();
const transition = reduceMotion ? { duration: 0 } : { type: 'spring', stiffness: 60, damping: 18 };
```

### Stable shell entrance
```tsx
<motion.div
  initial={reduceMotion ? false : { opacity: 0, y: 12 }}
  animate={reduceMotion ? {} : { opacity: 1, y: 0 }}
  transition={{ duration: 0.35, ease: 'easeOut' }}
/>
```

### Defer decorative motion, not input affordances
```tsx
const heroDecorVisible = !reduceMotion;
// decorative layers animate; inputs retain stable position and target size
```
