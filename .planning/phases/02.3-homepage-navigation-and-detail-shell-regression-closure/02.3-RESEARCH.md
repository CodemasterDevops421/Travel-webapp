# Phase 02.3: Homepage Navigation and Detail Shell Regression Closure - Research

**Researched:** 2026-03-11
**Domain:** homepage discovery-card navigation, shared preference-aware links, hotel-detail shell utility contracts
**Confidence:** HIGH

## Summary

Phase `02.3` should be planned as a **targeted regression-closure phase**, not a cleanup or redesign phase. The repo already shows both the broken state and the prior working contracts:

- homepage cards were regressed from `PreferenceLink`-wrapped interactive cards into inert `<article>` blocks with only `cursor-pointer`
- hotel-detail components still depend on legacy shell classes that were removed from `src/app/globals.css`
- the repo already favors narrow Vitest source-contract tests for UI regression guardrails, so this phase should extend that pattern instead of introducing broad snapshots or a multi-surface refactor

The safest implementation is:

1. restore the previous per-card `PreferenceLink` wrapping for homepage modules
2. restore the removed CSS utility classes additively in `globals.css`
3. add focused regression tests that lock those exact contracts

Do not use this phase to migrate hotel-detail callers to newer surface tokens or redesign homepage card destinations.

## Current Regressions And Exact Restore Targets

### Regression 1: Homepage cards lost navigation

Current state in:

- `src/components/home/featured-deals-strip.tsx`
- `src/components/home/travel-articles.tsx`
- `src/components/home/trending-destinations.tsx`

Each file now renders clickable-looking `<article>` cards with hover styling and `cursor-pointer`, but no actual anchor or `PreferenceLink` wrapper. That breaks:

- mouse click-through
- keyboard tab/enter navigation
- stored language/currency preference propagation

### Exact restore target for homepage cards

Git history shows the working pre-regression contract in commit `3701ae0`:

- `FeaturedDealsStrip` wrapped each card in:
  - `PreferenceLink`
  - `href={`/search?q=${encodeURIComponent(deal.city)}`}`
  - focus-visible ring classes on the link wrapper
- `TravelArticles` wrapped each card in:
  - `PreferenceLink`
  - `href={`/search?q=${encodeURIComponent(article.tag)}`}`
  - the same focus-visible ring classes
- `TrendingDestinations` wrapped each card in:
  - `PreferenceLink`
  - `href={`/search?q=${encodeURIComponent(item.name)}`}`
  - the same focus-visible ring classes

This is the lowest-risk restore target because it is already proven in repo history and matches the phase context instruction to restore the previous preference-aware behavior rather than leaving generic section-level `/search` links as the only working navigation.

### Routing nuance that matters for planning

The repo has a newer canonical destination route layer:

- `src/features/search/lib/destination-seo.ts`
- `src/app/stays/[destination]/page.tsx`

Known destinations already map cleanly to `/stays/{slug}` for:

- `bali`
- `dubai`
- `kyoto`
- `tokyo`
- `zurich`

Unknown-but-valid slugs also resolve through `/stays/[destination]` with generic metadata. That means a later follow-up refactor could migrate some homepage cards from `/search?q=...` to `/stays/{slug}`. That is **not** the safest closure move for this phase. The safest closure move is to restore the exact pre-regression link contract first.

### Regression 2: Hotel-detail shell utilities were removed

Current state:

- hotel-detail components still use `surface-shell`, `surface-shell-subtle`, `page-shell`, and `page-section`
- `src/app/globals.css` now defines `surface-panel` and `surface-subtle`, but no longer defines those legacy hotel-detail shell classes

Affected callers confirmed in current source:

Git history shows the removed contract in `src/app/globals.css` from commit `d7ee6eb`:


## Reusable Patterns Already In Repo

### Pattern 1: `PreferenceLink` is the route-aware navigation contract

`src/components/navigation/preference-link.tsx` resolves `href` through:

- store language from `useSearchUIStore`
- store currency from `useSearchUIStore`
- `normalizeLanguage`
- `normalizeCurrency`
- `withPreferenceParams`

`withPreferenceParams` only mutates local app routes and only injects `language` / `currency` when missing. That makes `PreferenceLink` the correct tool for homepage card restoration.

### Pattern 2: Existing card navigation precedent already exists

`src/features/search/components/horizontal-hotel-card.tsx` is the clearest reusable precedent:

- image wrapped in `PreferenceLink`
- hotel title wrapped in `PreferenceLink`
- location/meta row wrapped in `PreferenceLink`
- CTA wrapped in `PreferenceLink`

The paired test `tests/search-results-card-behavior.test.tsx` already locks this behavior with a source-level contract. Phase `02.3` should mirror that approach for homepage modules.

### Pattern 3: CSS utility contracts are already treated as source-level guardrails

The repo already uses source-oriented contract tests for CSS and layout behavior:

- `tests/homepage-motion-contract.test.ts`
- `tests/homepage-hero-parity.test.ts`
- `tests/hotel-detail-content.test.ts`
- `tests/hotel-booking-card.test.ts`

These tests do not try to snapshot rendered CSS output. They assert that specific source-level classes, strings, and structural seams exist. That is the right pattern for restoring legacy shell utilities.

### Pattern 4: Hotel-detail composition is already centralized

Current hotel-detail composition is concentrated in:

- `hotel-detail-experience.tsx`

Because the class usage is centralized and already stable, restoring the global utility definitions is safer than touching every hotel-detail section component.

## Architecture Patterns

### Pattern 1: Additive Regression Closure

Restore missing contracts where they used to exist instead of renaming active callers.

Use for:

- `PreferenceLink` card wrappers
- legacy shell utility class restoration

Why:

- minimum blast radius
- aligns with phase scope guardrails
- avoids mixing closure work with refactor work

### Pattern 2: Source-Contract Guardrails

Lock the exact strings and wrappers that define the regression boundary.

Use for:

- homepage card link wrappers and href expressions
- restored `globals.css` utility blocks
- confirmation that hotel-detail callers still use the restored classes

### Pattern 3: Behavior Test Only Where It Adds Real Signal

Rendered interaction tests should be used for keyboard/mouse semantics where source assertions alone would miss behavior.

Best fit in this phase:

- homepage card keyboard/tab/enter reachability for at least one representative module

Not necessary in this phase:

- broad visual snapshots
- full hotel-detail rendering snapshots

## Safest Closure Strategy Versus Broader Refactor

### Recommended closure strategy

1. Rewrap homepage cards with `PreferenceLink` using the exact pre-regression destination expressions.
2. Restore the four removed shell utilities in `src/app/globals.css`.
3. Add narrow tests that assert:
   - each homepage module imports and uses `PreferenceLink`
   - each module restores its prior per-card href expression
   - `globals.css` contains the four restored utility blocks
   - hotel-detail source still depends on those classes

### Why this is safest

- it matches known-good repo history
- it avoids changing hotel-detail component architecture
- it keeps the route decision conservative
- it fits the repo’s existing testing style

### What not to do in this phase

- do not migrate hotel-detail callers from `surface-shell` to `surface-panel`
- do not redesign the homepage card taxonomy
- do not convert all homepage cards to `/stays/{slug}` just because canonical routes now exist
- do not bundle a global CSS token cleanup with this work

### Acceptable limited improvement if planning needs one

If planners want one small forward-looking adjustment, allow a helper for homepage card href generation only if it preserves the old destination behavior exactly and does not widen scope. That is optional, not required.

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| Preference-aware navigation | Custom link helper or manual query concatenation in each card | `PreferenceLink` | Existing contract already normalizes and appends preferences safely |
| Hotel-detail surface migration | New token-mapping layer for this phase | Additive restoration of `surface-shell*` and `page-*` classes | The callers already exist and the phase is regression-only |
| Visual protection | Large snapshots or end-to-end suite first | Narrow Vitest source-contract tests plus one focused interaction seam | Faster, more stable, aligned with repo conventions |
| Destination canonicalization cleanup | Full rewrite of homepage href patterns | Exact pre-regression href expressions | Lowest-risk restore target |

## Common Pitfalls

### Pitfall 1: Restoring clickability without keyboard semantics

If cards stay as bare `<article>` blocks with click handlers, the regression remains partially open. Use actual links.

### Pitfall 2: Replacing `PreferenceLink` with raw `Link`

That would restore navigation but silently drop stored language/currency propagation.

### Pitfall 3: Replacing class usage instead of restoring class definitions

Changing every hotel-detail caller to newer utility names expands risk and scope for no regression-closure benefit.

### Pitfall 4: Locking only section-level links

The current “View all deals” and “Browse all guides” links are not sufficient. The regression is at the per-card interaction layer.

### Pitfall 5: Overfitting to `/stays/{slug}` now

Canonical destination routes exist, but the known-good homepage behavior in repo history used search-query links. Mixing restoration with route modernization increases planning uncertainty.

## Validation Architecture

### Objective

Prove that homepage discovery cards are real preference-aware links again and that the hotel-detail shell utilities exist again as stable global contracts.

### Automated checks

1. Source-contract test for homepage card restoration
   - verifies `PreferenceLink` imports
   - verifies per-card wrappers
   - verifies exact href expressions
   - verifies inert card-only regression pattern is absent

2. Source-contract test for restored shell utilities
   - verifies `globals.css` defines `surface-shell`
   - verifies `surface-shell-subtle`
   - verifies `page-shell`
   - verifies `page-section`
   - verifies active hotel-detail sources still consume those classes

3. Existing neighboring regression suites stay green
   - `tests/search-results-card-behavior.test.tsx`
   - `tests/hotel-booking-card.test.ts`
   - `tests/hotel-detail-content.test.ts`

4. Optional focused jsdom link behavior test
   - verifies at least one homepage card is keyboard-focusable as a link
   - verifies resolved href includes preference params

### Manual checks

1. Homepage on desktop
   - each featured deal card opens a destination/search route on click
   - tab navigation reaches the cards
   - enter activates the focused card

2. Homepage on mobile-width
   - cards remain links and preserve visual affordance

3. Hotel detail page
   - hero, booking rail, reviews, rooms, and supporting sections render with card chrome again
   - page width and section spacing look restored, not collapsed or flat

### Exit criteria

- homepage cards are links, not inert containers
- stored language/currency preferences continue to propagate through homepage card navigation
- restored shell utility classes are present in `globals.css`
- hotel-detail shell chrome no longer depends on missing CSS utilities
- focused regression suite passes without broad unrelated failures
